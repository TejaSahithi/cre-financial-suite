# Architecture Decision Log

> Generated: 2026-07-20 · Repository revision: `34563cfaff4271b72d00b0841353dc2792f2f16a` (branch `feature/lease-intelligence-enterprise-p1-p8`) · Part of the [Project Audit](README.md)

Decisions evident in the code but never captured as formal ADRs. Recorded here so they can be ratified, revisited, or superseded deliberately rather than by default. Full narrative: [02 — Architecture decision summary](02-current-state-architecture.md#architecture-decision-summary).

| # | Decision | Evidence | Likely context | Benefits | Tradeoffs | Current consequences | Disposition |
|---|---|---|---|---|---|---|---|
| AD-01 | Supabase as the entire backend (Postgres+Auth+Storage+Functions) | 163 tables, 82 functions, `supabase/` | Small-team velocity after leaving Base44 ([ARC-002](findings-register.md#arc-002)) | Fast delivery; integrated platform | Single-project blast radius; vendor coupling; no evidenced staging strategy | Product built quickly but has no environment-promotion story ([14](14-devops-infrastructure-and-delivery.md)) | **Retain**; formalize with an explicit ADR + environment topology plan |
| AD-02 | Dual data-access path: direct RLS reads from the browser + service-role edge functions for compute | `src/services/api.js` vs `edgeFunctions.js` | CRUD simplicity for reads; heavy logic needs elevated privileges | Right tool per job; RLS as a genuine safety net for direct reads | Two authorization models to keep consistent; RLS bypassed for the majority of writes | Root cause of [SEC-001](findings-register.md#sec-001) | **Reconsider** — evaluate pushing more read paths to user-scoped clients; document the split explicitly |
| AD-03 | Business logic split between large client-side services (100–174 KB) and edge functions | `expenseService.js`, `parsingEngine.js`, `leaseExpenseRuleService.js` | Iterative migration from a more client-heavy origin | Working product, fast iteration | Duplicated validation/logic risks drift ([06 §2](06-frontend-backend-integration.md)) | No shared contract layer; client and server can silently diverge | **Reconsider incrementally** — document canonical owner per domain concept, don't rewrite wholesale |
| AD-04 | Durable job table (`pipeline_jobs`) instead of a message queue | EV-16 | Avoid new infra; Supabase has no native queue product | Simple, inspectable, supports cancel/retry/durability reconciliation | No scheduler, no reaper, no fan-out ([OPS-006](findings-register.md#ops-006)) | Stuck jobs can stall silently | **Retain at current scale**; add a scheduler + reaper; write the ADR now while the tradeoff is still fresh |
| AD-05 | File-based page registry with a generated route config (71 pages) | `src/pages.config.js` | Convention over configuration for rapid page addition | Trivial to add pages | Route-level auth must stay manually synced with `rbac.js` maps | Parallel-maintained client/server authorization models ([06 §5](06-frontend-backend-integration.md), R15) | **Retain**; add a route-guard consistency test |
| AD-06 | Client-supplied `x-acting-org-id`, always server-validated | EV-05 | Support multi-org users and super-admin cross-tenant operations safely | Explicit, audited tenancy selection; already survived one internal security fix ([TEN-003](findings-register.md#ten-003)) | Header is part of the security surface — must never be trusted without validation (it isn't) | Works as designed | **Retain**; document the invariant explicitly as an ADR so future contributors don't "simplify" it into trusting the header |
| AD-07 | Three accepted forms of internal service-to-service authentication, two reusing the service-role key | [SEC-003](findings-register.md#sec-003) | Organic growth of the pipeline/worker auth pattern over time | Functions can call each other without full user-JWT machinery | Service-role key doubles as an API password; wider audit surface | Works, but is the single highest-leverage security cleanup identified | **Reconsider** — collapse to one dedicated, rotatable internal secret |
| AD-08 | Multi-provider AI abstraction (Vertex/Azure/Anthropic/Docling, env-switchable) | EV-19 | Avoid single-vendor AI lock-in; hedge provider outages/pricing | Resilience; negotiating leverage; kill-switch exists | More integration surface to maintain and test | No automatic failover — switching is manual (env change) | **Retain**; consider automatic failover as a later reliability investment |
| AD-09 | In-memory seed-data fallback when Supabase env vars are absent | [WKF-002](findings-register.md#wkf-002) | Enable demos/dev without a live backend | Great for `DemoExperience` and offline dev | Dangerous if it activates in a misconfigured production build — writes silently vanish | Real risk, not yet triggered per known evidence | **Reconsider** — should be explicitly demo-only, never a silent production fallback |
| AD-10 | Extensive in-repo phase documentation (~70 files) instead of external project-management tooling | `docs/` | Solo-maintainer context preservation | Exceptional traceability of intent over time; enabled this audit | Stale docs risk being read as current state ([PRD-001](findings-register.md#prd-001)) | Mostly positive; needs "historical" labeling discipline | **Retain** with clearer historical/current labeling going forward |
